# Архитектура Emayka Store

## Цели

Интернет-магазин одежды с отдельной витриной, API и административной панелью. Архитектура должна позволять заменить внутренний складской контур на МойСклад или 1С без переписывания каталога, корзины и оформления заказа.

## Компоненты

- **Frontend:** Next.js (App Router), TypeScript. Отвечает за страницы магазина, авторизацию покупателя, корзину и личный кабинет.
- **Backend:** Laravel. Единый API, бизнес-правила, каталог, цены, остатки, заказы, возвраты, интеграции.
- **Admin:** Filament внутри Laravel. Управление контентом, заказами, возвратами, пользователями и настройками интеграций.
- **Database:** PostgreSQL как основная транзакционная БД.
- **Queue/cache:** Redis + Laravel Queue для уведомлений, синхронизаций, обращений к службам доставки и повторной обработки webhook.
- **Files:** S3-совместимое хранилище для изображений товаров и вложений возврата.

## Границы доменов backend

1. Catalog — товары, категории, коллекции, медиа, атрибуты.
2. Inventory — SKU, варианты цвета/размера, доступный остаток и резервы.
3. Cart & Checkout — корзина, проверка цены/остатка, адрес и способ доставки.
4. Orders — заказ, позиции, снимок цены и товара на момент покупки, статусы.
5. Payments — платёжные попытки, idempotency, webhook и сверка неопределённых платежей.
6. Shipping — единый интерфейс провайдеров Яндекс, Ozon и СДЭК.
7. Returns — заявки, причины, фото, QR/штрихкод обратной отправки.
8. Content — главная, баннеры, подборки и управляемые блоки.
9. Accounts — покупатели, адреса, избранное и история заказов.
10. Notifications — email и системные уведомления.

## Ключевые решения

### SKU и остатки

Вариант товара (например, модель + цвет + размер) имеет собственный SKU. Внутренний адаптер InventoryProvider изолирует источник остатков. Первая реализация — локальная БД. Внешние системы подключаются через тот же контракт.

Доступное количество = физический остаток минус активные резервы. Резерв создаётся транзакционно с блокировкой строки/условным обновлением, чтобы два покупателя не могли купить последнюю единицу. У резерва есть срок действия и задача освобождения.

### Заказ и оплата

Создание заказа, фиксация цены и резервирование остатков выполняются в транзакции БД. Платёжная попытка хранится отдельно от заказа. Webhook обрабатывается идемпотентно по идентификатору события/операции. Если пользователь видит списание, но callback не пришёл, заказ не переводится автоматически в ошибку: платёж получает состояние проверки, после чего выполняется запрос статуса у провайдера и/или периодическая сверка.

### Доставка

ShippingProvider — общий контракт для расчёта стоимости, получения вариантов доставки/ПВЗ, создания отправления, получения этикетки/кода и отмены. Отдельные адаптеры Яндекс, Ozon и СДЭК. Секреты и ключи хранятся только на backend.

### Контент главной

Контентные блоки хранятся структурированно и редактируются в Filament: тип блока, порядок, активность, даты показа и данные. Не требуется выпускать frontend-релиз для перестановки баннеров и подборок.

### Возвраты

Покупатель создаёт заявку по позиции заказа, указывает причину и прикладывает фотографии. Backend создаёт обратное отправление через поддерживаемого перевозчика и отправляет email с инструкцией и QR-кодом, если провайдер предоставляет такой сценарий. До подтверждения API перевозчика нельзя обещать наличие QR у любого тарифа.

## Рекомендуемая структура репозитория

- `backend/` — Laravel API + Filament.
- `frontend/` — Next.js storefront.
- `docs/` — архитектура, требования, API-контракты и решения.
- `infra/` — локальная инфраструктура и deployment templates.

## Безопасность и надёжность

- Проверка прав доступа к каждому заказу и возврату по владельцу.
- Валидация всех входных данных и ограничение размера/типа загружаемых файлов.
- Секреты только в переменных окружения/secret manager.
- Идемпотентность платежных и складских операций.
- Логирование внешних запросов без платёжных секретов и персональных данных.
- Повторные попытки очередей с backoff и dead-letter/failed jobs.
- Аудит действий администраторов.
